## 1. 잘한 선택들

### DDD를 프로젝트 목표로 잡은 것

이 프로젝트에서 가장 잘한 선택을 꼽으라면 DDD입니다. "서비스에 다 때려넣지 말고, 도메인 객체가 비즈니스 로직을 가지게 하자"는 목표를 세우고, User 엔티티에 `canManageLabApplications()`, `canViewLabNotices()` 같은 메서드를 넣었습니다. Password를 `@Embeddable` 값 객체로 만든 것도 DDD의 Value Object를 직접 경험하기 위해서였습니다.

이렇게 하니까 단위 테스트가 확실히 쉬워졌습니다. "이 사용자가 이 랩의 공지를 볼 수 있나?"라는 질문에 서비스가 아니라 User 객체가 직접 답할 수 있게 된 거니까요. 다음 프로젝트에서도 DDD는 반드시 적용할 생각입니다.

### 이메일 교체에서 헥사고날의 가치를 직접 증명한 것

헥사고날 아키텍처 자체는 과했습니다. 근데 8월에 Google SMTP에서 Mailjet으로 바꿀 때, Adapter 하나만 수정하고 도메인/서비스 코드를 한 줄도 안 건드린 경험은 진짜 값졌습니다. "포트와 어댑터"가 이론이 아니라 실제로 동작하는 걸 직접 본 순간이었습니다. 과한 적용이라는 실패 속에서 건진 성공이라고 할 수 있습니다.

### 테스트 팩토리를 처음부터 만든 것

프로젝트 초기부터 22개의 테스트 팩토리를 만들어놓으니까, `DomainUserFactory.createAdmin()` 한 줄이면 끝이었습니다. 90개 넘는 테스트에서 일관된 데이터를 쓸 수 있었고, 엔티티 생성자가 바뀌어도 팩토리만 고치면 됐습니다.

다만 리팩터링이 깊어질수록 팩토리 유지보수 자체가 부담이 되기도 했습니다. 규모가 더 컸으면 FixtureMonkey 같은 라이브러리가 필요했을 것 같습니다.

### Swagger를 프론트엔드 소통 수단으로 쓴 것

21개 컨트롤러에 @Tag를 적용하고 JWT 보안 설정까지 넣은 Swagger UI가 React 팀과의 주요 소통 수단이었습니다. 별도 API 문서 만들 필요 없이 코드와 문서가 동기화되는 환경이었습니다.

### 배포 파이프라인에 사전 검증을 넣은 것

CI/CD에서 QR 시크릿 키 길이를 빌드 시점에 검증하게 한 건 작은 변경이었지만, 운영 환경에서 런타임 에러를 사전에 막아줬습니다. 작은 거지만, 이런 게 운영 경험이구나 싶었습니다.

## 2. 아쉬운 선택들

### 헥사고날 아키텍처를 전면 적용한 것

토비의 스프링에서 "모듈만 교체하면 된다"는 개념에 꽂혀서 전면 적용했는데, 보일러플레이트의 비용을 너무 만만하게 봤습니다.

52개 Port 인터페이스와 21개 Adapter, 그 중 20개가 JPA Repository를 그대로 호출하는 단순 위임 코드. 당초 목표였던 MySQL → PostgreSQL 교체와 Redis 도입은 결국 못 했습니다. 보일러플레이트 관리하느라 새 기능 개발이 느려졌고, 교체할 여유 자체가 없었습니다. 교체를 하려고 헥사고날을 넣었는데, 헥사고날 때문에 교체를 못 한 셈입니다.

이메일처럼 실제로 교체가 발생하는 곳에서만 Port를 두는 **선택적 적용**이 맞았을 것 같습니다.

→ 상세: [ARCHITECTURE.md #1](ARCHITECTURE.md#1-헥사고날-아키텍처-전환)

### Command/Query 분리를 활용하지 못한 것

DB 쿼리 최적화의 기반을 만들겠다고 36개의 UseCase 인터페이스를 Command/Query로 나눴는데, 읽기 전용 레플리카나 캐시 같은 최적화까지는 못 갔습니다. `@Transactional(readOnly = true)` 수준의 이점만 얻었고, 인터페이스 수 폭발이라는 비용을 치렀습니다.

코드 가독성은 좋아졌지만, 이것도 헥사고날과 같은 문제였습니다. "미래를 위한 선제적 분리"인데 그 미래가 안 왔습니다.

→ 상세: [ARCHITECTURE.md #5](ARCHITECTURE.md#5-command--query-분리)

### 수동 DTO 매핑 (MapStruct를 몰랐음)

DTO 69개(Request 33개, Response 28개, 기타 8개)를 전부 수동으로 매핑했습니다. MapStruct나 ModelMapper 같은 매핑 라이브러리가 있는 줄 몰랐습니다. 나중에 알게 됐을 때는 이미 수동 매핑이 전체에 퍼져 있어서 전환 비용이 컸습니다.

필드가 추가될 때마다 여러 곳을 찾아다니며 수정해야 했습니다. 공부 부족이 직접적인 원인이었고, 다음 프로젝트에서는 반드시 MapStruct를 쓸 생각입니다.

### H2 테스트 DB (Testcontainers를 몰랐음)

테스트에서 H2 인메모리 DB를 썼습니다. 빠르고 간편한 건 좋았지만, MySQL 특화 기능을 테스트할 수 없는 한계가 있었습니다. Testcontainers의 존재를 몰랐기 때문에 "빠르게 가자"며 H2를 선택한 건데, 알았으면 실제 MySQL 컨테이너로 테스트했을 것 같습니다.

### JaCoCo 빌드 강제를 꺼버린 것

도메인 95%, 서비스 90%, 어댑터 85%라는 커버리지 규칙을 설정해놓고, 빌드가 계속 실패하니까 `check` 태스크를 주석 처리해버렸습니다. 커버리지 리포트는 생성되지만 기준 미달이어도 빌드가 통과하는 상태입니다.

높은 기준을 세운 의도는 좋았는데, 개발 초기에 기능 구현과 커버리지를 동시에 달성하는 건 현실적으로 힘들었습니다. 처음에는 낮게 잡고 점진적으로 높이는 게 맞았을 것 같습니다.

### Checkstyle/PMD를 포기한 것

코드 품질 도구를 넣어보겠다고 Checkstyle과 PMD를 설정했는데, 경고가 쏟아져서 비활성화했습니다. 도구 자체의 문제가 아니라, 기본 설정 그대로 시작한 게 원인이었습니다. 프로젝트에 맞게 커스터마이징을 먼저 했어야 합니다.

### 권한 시스템을 처음부터 설계하지 않은 것

권한에 대한 학습이 부족한 상태에서 시작해서 3번의 큰 변경을 거쳤습니다(단순 Role → @PreAuthorize → 통합 권한 평가기). 각 단계에서 부족함을 느끼고 개선한 과정 자체는 의미 있었지만, 초기에 더 공부했으면 @PreAuthorize 단독 단계는 건너뛸 수 있었을 것 같습니다.

→ 상세: [ARCHITECTURE.md #4](ARCHITECTURE.md#4-권한-시스템의-3단계-진화)

### 레거시 API 엔드포인트를 안 치운 것

기능을 개선하면서 이전 API와 새 API가 공존하게 됐는데, `@Deprecated`만 붙여놓고 실제로 안 지웠습니다. "나중에 정리하겠지"가 결국 안 한 거랑 마찬가지였습니다.

## 3. 프론트엔드 협업

### React 팀과의 작업

백엔드 API가 어느 정도 갖춰진 시점에서 React 팀과 협업했습니다. Swagger UI가 주요 소통 수단이었고, 프론트엔드 코드는 이 저장소에 포함되어 있지 않습니다.

API를 직접 소비하는 프론트엔드 입장의 피드백을 받으면서, "이 응답 구조가 프론트에서 쓰기 불편하겠다"라는 감각이 생겼습니다. CORS 설정, 에러 응답 형식, 역직렬화 문제 같은 것들이 프론트 연동 시점에 한꺼번에 터졌습니다. CORS 때문에 `hotfix: cors 설정`이라는 커밋을 쳤던 게 기억납니다. API 스펙을 먼저 확정하고 개발했으면 이런 문제를 줄일 수 있었을 것 같습니다.

**현재 상태**: 프론트엔드와 함께 배포까지 완료했지만, 프론트엔드 서버가 현재 운영되고 있지 않아 웹 UI로는 접속할 수 없습니다. 백엔드 API는 Swagger UI를 통해 확인할 수 있습니다.

## 4. 프로젝트를 통해 성장한 점

### "이 코드를 어디에 넣어야 하는가?"를 고민하게 됐습니다

헥사고날 아키텍처를 적용하면서 레이어 간 의존성 방향을 의식적으로 관리하는 습관이 생겼습니다. 과도한 적용이라는 실패를 겪었지만, 그 실패 덕분에 "언제 추상화가 필요하고 언제 과도한지"를 판단할 수 있는 감각이 생겼습니다. 실패 안 해봤으면 이 감각은 안 생겼을 것 같습니다.

### 보안은 나중에 붙이는 게 아니라는 걸 체감했습니다

JWT 토큰 3번의 시행착오, 권한 시스템 3단계 진화, QR 토큰 암호화 — 이것들을 직접 겪으면서 보안은 설계 단계부터 고려해야 한다는 걸 몸으로 느꼈습니다. 특히 JWT 리프레시 토큰을 "임시 해결책"으로 7일 만료로 올려놓은 게 오히려 새로운 보안 취약점이 될 뻔한 경험은 잊을 수가 없습니다. 실제 커밋에 `# 현재 7일로 임시 처리`라는 주석을 남겨놨는데, 그게 얼마나 위험한 건지 나중에야 알았습니다.

### "왜 어렵다고 하는지"를 코드로 이해했습니다

토비의 스프링에서 읽은 이론과 실제 적용 사이의 간극을 직접 경험했습니다. 헥사고날이 왜 "필요할 때만 하라"는지, Command/Query 분리가 왜 "실제 필요가 있을 때" 도입하라는지, 6단계 Role이 왜 권한 관리를 복잡하게 하는지 — 이런 걸 교과서가 아니라 52개 Port 인터페이스와 SecurityConfig 12번 수정으로 이해했습니다.

### 처음으로 코드를 서비스로 배포해봤습니다

GitHub Actions + AWS EC2 배포를 직접 구축한 게 인생 첫 CI/CD 파이프라인이었습니다. Jenkins은 별도 학습이 필요하다고 들어서 GitHub Actions를 선택했는데, CI/CD yaml 파일을 25번 수정하면서 "코드를 작성하는 것"과 "서비스로 제공하는 것" 사이의 간극을 이해하게 됐습니다. data.sql을 28번 수정한 것도, 환경별로 데이터가 달라야 한다는 걸 운영하면서 알게 된 거였습니다.

## 5. 다시 시작한다면

### 처음부터 할 것

- **헥사고날은 선택적으로**: 이메일, 파일 업로드처럼 실제 교체가 예상되는 곳에서만 Port를 두고, 나머지 Repository는 직접 의존
- **API 스펙 먼저 확정**: OpenAPI 3.0 스펙을 먼저 작성하고, 프론트랑 동시에 개발 시작
- **권한 설계를 초기에**: 도메인별 권한 매트릭스를 문서화한 뒤 구현 (SecurityConfig 12번 수정은 하고 싶지 않습니다)
- **MapStruct 도입**: 수동 DTO 매핑의 반복 제거
- **Testcontainers 사용**: H2 대신 실제 MySQL 컨테이너로 테스트
- **Git Flow 적용**: main(운영), develop(개발), feature/*(기능)으로 브랜치 전략 명확화
- **Swagger 문서화를 기능 개발과 동시에**: 기능 PR에 문서화 필수 포함

### 하지 않을 것

- "열심히 하면 되겠지"로 모든 레이어에 추상화 적용하는 것
- 레거시 API를 "나중에 정리하겠다"며 방치하는 것
- 개발 환경에서 모든 권한을 허용하는 것 (운영까지 버그를 숨기는 원인이 됨)
- "임시 해결책"을 운영에 배포하는 것 (JWT 7일 만료 같은 짓)
- JaCoCo를 처음부터 높은 기준으로 강제하는 것 (점진적으로)
- Checkstyle을 기본 설정 그대로 시작하는 것 (프로젝트에 맞게 커스터마이징 먼저)
