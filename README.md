# Rankus - 대학교 랩실 통합 관리 플랫폼

> 대학교 연구실(랩실) 정보 비대칭 문제를 해결하고, 랩 탐색부터 지원 · 운영 · 랭킹까지 하나의 플랫폼에서 관리하는 백엔드 서비스

## 프로젝트 소개

### 왜 만들었는가

대학교에서 연구실(랩)을 선택할 때, 학생들이 참고할 수 있는 정보가 부족합니다. 어떤 랩이 있는지, 분위기는 어떤지, 연구 실적은 어떤지 알기 어렵고, 랩 운영자 입장에서도 지원자 관리, 출결, 일정 등을 체계적으로 관리할 도구가 없었습니다.

Rankus는 이 **정보 비대칭 문제**를 해결하기 위해 만든 플랫폼입니다.

- **학생**: 랩을 탐색하고, 지원서를 제출하고, 면접 일정을 잡을 수 있습니다.
- **랩 운영진**: 멤버 관리, QR 출석, 투표, 공지, 자료실, 일정 관리를 한 곳에서 처리합니다.
- **랭킹 시스템**: 논문, 수상, 자격증 등을 점수화해서 랩 간 건전한 경쟁을 유도합니다.

### 프로젝트 구성

프론트엔드는 React 팀과 협업하여 개발했으며, API 문서(Swagger) 기반으로 소통했습니다. 본 저장소는 **백엔드(Spring Boot)** 코드만 포함하고 있으며, REST API 100개 이상, 도메인 엔티티 31개로 구성되어 있습니다.

## 주요 기능

### 핵심 기능

#### 랩 탐색 & 지원

학생이 랩을 검색하고, 지원서를 제출하고, 면접 시간대를 선택하는 흐름입니다.

- 랩 목록 조회 (카테고리별 필터링, 이미지 포함)
- 지원서 제출 → 면접 슬롯 선택 → 승인/거절 워크플로우
- **면접 슬롯 동시성 제어**: 마지막 1자리를 여러 학생이 동시에 선택하는 문제를 MySQL `SELECT FOR UPDATE` 비관적 락 + 재시도 로직으로 해결했습니다. → [상세: 동시성 제어](docs/TROUBLE_SHOOTING.md#2-면접-슬롯-동시-예약-동시성-제어)

#### 랭킹 시스템

랩별 실적을 점수화하여 투명한 비교 기준을 제공합니다.

- 13개 점수 카테고리 (논문, 학회, 수상, 자격증, 경진대회 등)
- 점수 제출 → 리더 승인/거절 → 랩 총점 반영
- 증빙 파일 첨부, 중복 제출 검증, 6개월 유효기간
- 기여도 기반 개인별 기여 점수 조회

#### QR 출석 시스템

랩 세미나나 정기 모임의 출석을 QR 코드 하나로 처리합니다.

- 출석 세션 생성 → QR 코드 발급 → 멤버가 스캔하여 체크인
- **QR 토큰 암호화 진화**: 초기에는 세션ID와 랩ID를 평문으로 연결한 토큰이었으나, 위변조 가능성을 인지하고 AES-256-GCM 인증 암호화로 전환했습니다. 레거시 호환을 위한 이중 포맷(Secure + Legacy fallback) 지원. → [상세: QR 토큰 암호화](docs/TROUBLE_SHOOTING.md#3-qr-토큰-보안-평문에서-aes-256-gcm까지)
- 실시간 출석 통계, 출석률 조회

### 랩 운영 기능

#### 투표

랩 내부 의사결정을 위한 투표 시스템입니다.

- 2~5개 선택지로 투표 생성, 마감 기한 설정
- 중복 투표 방지, 실시간 참여율 조회
- 수동 조기 마감 가능, 생성자만 관리

#### 공지사항

일반 공지와 긴급 공지를 구분하여 관리합니다.

- 일반(NOTICE) / 긴급(URGENT) 타입 분리
- 고정(Pin) 기능으로 중요 공지 상단 노출
- 페이지네이션 + 고정 공지 우선 정렬

#### 자료실

랩 내부 자료를 카테고리별로 관리하고 공유합니다.

- 7개 카테고리: 강의노트, 과제, 연구자료, 참고문헌, 문서, 소프트웨어, 기타
- 파일 업로드/다운로드, 공개/비공개 전환
- 내가 올린 자료 조회, 자료 통계

#### 캘린더

랩 일정을 관리하며, 면접 일정은 면접 시스템에서 자동 연동됩니다.

- 일반 일정: 수동 등록/수정/삭제
- 면접 일정: 면접 생성 시 자동으로 캘린더에 반영 (수동 편집 불가)
- 두 캘린더를 분리하여 혼동 방지

#### 대시보드

랩 현황을 한눈에 파악할 수 있는 통합 대시보드입니다.

- 최근 공지 3건, 진행 중인 투표 3건, 공개 자료 3건, 다가오는 일정 3건, 최근 가입 멤버 3건을 집계
- 출석률 통계, 멤버 현황 조회

### 인프라 기능

#### 인증 & 이메일 인증

회원가입부터 로그인까지의 인증 흐름입니다.

- 대학교 이메일(@hs.ac.kr)로만 가입 가능, 6자리 인증코드 발송
- JWT 액세스 토큰(15분) + 리프레시 토큰(7일) 로테이션 방식
- 로그아웃 시 토큰 블랙리스트 등록으로 즉시 무효화
- **리프레시 토큰 3번의 시행착오**: 1분(테스트용) → 7일 고정(로테이션 무의미) → 15분+7일 분리(정상). 각 단계에서 왜 그런 선택을 했고, 왜 실패했는지를 기록했습니다. → [상세: JWT 리프레시 토큰](docs/TROUBLE_SHOOTING.md#1-jwt-리프레시-토큰-3번의-시행착오)

#### 6단계 역할 기반 권한 시스템

```
ADMIN > PROFESSOR > LAB_LEADER > LAB_MANAGER > LAB_MEMBER > STUDENT
```

모든 API에 역할 기반 접근 제어가 적용되어 있으며, 권한 검증은 3단계로 이루어집니다.

1. **URL 레벨**: Spring Security 필터에서 인증 여부 확인
2. **메서드 레벨**: `@PreAuthorize`로 역할 검증
3. **도메인 레벨**: `UnifiedPermissionEvaluator` → 11개 도메인별 `PermissionHandler`가 "이 사용자가 이 랩의 이 리소스에 접근할 수 있는가"를 도메인 객체에게 질의

이 구조에 도달하기까지 산발적 role 체크 → @PreAuthorize → 통합 도메인 권한 평가기의 3단계 진화를 거쳤습니다. → [상세: 권한 시스템 진화](docs/ARCHITECTURE.md#4-권한-시스템의-3단계-진화)

#### 파일 관리

증빙 서류, 프로필 이미지, 자료실 파일을 통합 관리합니다.

- 파일 형식 제한 (PDF, JPG, PNG), 10MB 용량 제한
- 소유자 기반 삭제 권한, 메타데이터 조회

## 기술적 하이라이트

이 프로젝트에서 가장 많은 고민과 시행착오를 겪은 부분들입니다. 각 항목에서 **왜 그런 선택을 했는지, 선택의 근거, 실패한 이유, 최종적으로 어떻게 해결했는지**를 기록했습니다.

### 헥사고날 아키텍처 전환

처음에는 Controller → Service → Repository의 전통적인 레이어드 아키텍처로 시작했습니다. 서비스가 JPA Entity와 DTO에 직접 의존하면서 테스트가 어려워지고, 리팩터링할 때마다 연쇄적으로 수정해야 하는 문제가 생겼습니다.

2025년 6월, 헥사고날 아키텍처(포트 & 어댑터)로 전면 전환했습니다. **79개 파일 변경, 4,495줄 삭제, 1,627줄 추가** — 기능은 동일한데 코드가 60% 줄었습니다. 도메인 모델이 프레임워크에서 독립되면서 테스트가 단순해지고, 서비스는 UseCase 인터페이스 기반으로 바뀌었습니다.

→ [상세: 헥사고날 전환 과정과 Before/After 코드 비교](docs/ARCHITECTURE.md#1-헥사고날-아키텍처-전환)

### 서비스 반환값 리팩터링 (DTO → 도메인 객체)

헥사고날 전환과 함께, 서비스 계층이 DTO를 반환하던 구조를 도메인 객체를 반환하도록 변경했습니다. **40개 파일, 3,633줄 삭제, 1,890줄 추가**. DTO 변환 책임을 컨트롤러(어댑터)로 옮겨 서비스가 순수한 비즈니스 로직에만 집중하도록 했습니다.

→ [상세: 서비스 반환값 리팩터링](docs/ARCHITECTURE.md#6-서비스-반환값-리팩터링)

### JWT 리프레시 토큰 — 3번의 시행착오

토큰 만료 설정을 3번 바꿨습니다. 각 시도에서 왜 그 값을 선택했고, 왜 실패했는지, 최종적으로 어떤 구조가 맞았는지를 코드와 함께 기록했습니다.

→ [상세: JWT 리프레시 토큰 여정](docs/TROUBLE_SHOOTING.md#1-jwt-리프레시-토큰-3번의-시행착오)

### 동시성 제어 — 면접 슬롯 레이스 컨디션

4명이 동시에 마지막 1자리 면접 슬롯을 예약하면 어떻게 되는가? Optimistic Locking이 아닌 Pessimistic Locking을 선택한 이유와, 재시도 로직 설계 과정을 기록했습니다.

→ [상세: 동시성 제어](docs/TROUBLE_SHOOTING.md#2-면접-슬롯-동시-예약-동시성-제어)

### QR 토큰 암호화 — 평문에서 AES-256-GCM까지

QR 토큰이 평문이면 어떤 보안 문제가 생기는지, GCM 모드를 선택한 이유, 레거시 호환을 위한 이중 포맷 설계를 기록했습니다.

→ [상세: QR 토큰 보안 강화](docs/TROUBLE_SHOOTING.md#3-qr-토큰-보안-평문에서-aes-256-gcm까지)

### 권한 시스템 3단계 진화

단순 `if (role == ADMIN)` → `@PreAuthorize` → 도메인 객체 기반 통합 권한 평가기. 5개 연속 커밋으로 진행된 이 과정에서, 각 단계의 한계와 다음 단계로 넘어간 이유를 기록했습니다.

→ [상세: 권한 시스템 진화](docs/ARCHITECTURE.md#4-권한-시스템의-3단계-진화)

## 아키텍처

헥사고날 아키텍처(포트 & 어댑터)를 적용하여, 도메인 로직이 프레임워크에 의존하지 않도록 설계했습니다.

```
┌──────────────────────────────────────────────────────────┐
│                     Adapter Layer                         │
│  ┌─────────────────┐            ┌──────────────────────┐ │
│  │  Controller (21) │            │  JPA Repository      │ │
│  │  REST API        │            │  Mail / QR / Excel   │ │
│  └────────┬────────┘            └──────────┬───────────┘ │
│           │ Input Port                      │ Output Port │
├───────────▼─────────────────────────────────▼────────────┤
│                   Application Layer                       │
│  ┌──────────────────────────────────────────────────┐    │
│  │  Service (Command / Query 분리)                   │    │
│  │  UseCase 인터페이스 기반 (36개)                    │    │
│  └──────────────────────┬───────────────────────────┘    │
├──────────────────────────▼───────────────────────────────┤
│                     Domain Layer                          │
│  ┌──────────────────────────────────────────────────┐    │
│  │  순수 도메인 모델 (31개 엔티티)                     │    │
│  │  비즈니스 규칙, 권한 검증 로직                      │    │
│  │  프레임워크 의존성 없음                             │    │
│  └──────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────┘
```

## 테스트 전략

도메인 모델의 비즈니스 로직에 가장 높은 커버리지를 요구하고, 테스트 팩토리 패턴으로 90개 이상의 테스트에서 일관된 데이터를 생성합니다.

```
JaCoCo 커버리지 기준:
├── 도메인 모델    → 95%
├── 서비스 계층    → 90%
├── 어댑터 계층    → 85%
└── 글로벌 기준    → 80% line / 70% branch
```

## 프로젝트 구조

```
rankus/src/main/java/org/univ/rankus/
├── adapter/
│   ├── in/web/              # REST 컨트롤러 (21개), DTO (Request/Response)
│   └── out/                 # JPA Repository 어댑터, QR, Excel, Mail 어댑터
├── application/
│   ├── port/in/             # Input Port — UseCase 인터페이스 (Command/Query)
│   ├── port/out/            # Output Port — Repository 인터페이스
│   └── service/             # UseCase 구현체 (Command/Query 분리)
├── domain/model/            # 순수 도메인 모델 (31개, 프레임워크 무의존)
│   ├── attendance/          # 출석 세션, 출석 기록, QR 토큰
│   ├── calendar/            # 캘린더 이벤트
│   ├── interview/           # 면접, 면접 슬롯
│   ├── lab/                 # 랩, 지원, 공지, 자료실, 이미지
│   ├── ranking/             # 점수 제출, 랭킹 정책
│   ├── user/                # 사용자, 인증, 토큰
│   ├── vote/                # 투표, 투표 옵션, 참여
│   └── file/                # 파일 업로드 정책
├── common/
│   ├── security/            # JWT, UnifiedPermissionEvaluator, 11개 PermissionHandler
│   └── exception/           # 글로벌 예외 처리, 도메인별 에러 코드
└── config/                  # Spring 설정 (프로필별 Security, CORS, Swagger)
```
